# Represent OS design and runtime

> **Closed exploration / learning artifact (2026-10-21).** The report and its infographic retain the researched options and proposed separate-workspace design. The owner questioned that design and subsequently clarified the broader Orkest-platform direction; it is not an accepted OS implementation plan. Keep the findings and artifacts via the [learning record](Represent%20exploration%20learning%20record.md), preserve [Visu's liked experience](../../guides/visu-experience.md), and continue [Represent within the Orkest platform](Represent%20within%20the%20Orkest%20platform.md) in design first. The original recommendation below is preserved as history.

**Recommendation:** build Represent Workspace as a project-focused web app first; make Alegor the companion beside the work, and add Linux compute only when an approved task needs to run code.

Represent should adopt the *feeling* of Dot’s persistent companion and visible workspace, while treating “Represent OS” as a project-centered web workspace—not as a Linux distribution or an always-running remote desktop. The supplied screenshot and OpenAI’s published Dot guide support a useful interaction pattern: persistent companion, visible work surface, clear run state, reviewable results, and a way to take control; they do not reveal Dot’s internal runtime. Skales was researched directly through its exact public repository and linked guide, but its proprietary application was not installed or run. For Grafe, Gource’s tested value is temporal storytelling—showing files and contributors changing over time—not explaining verified code structure; the best design combines a stable evidence-linked map with an optional evolution view. The current Alegor MVP already supplies manual Git/docs snapshots, and Grafe supplies bounded JS/TS exploration, so neither needs a container for its present work. Start with a lightweight workspace that opens those real tools; attach local or isolated compute only when a real workflow must execute project code. This recommendation is a research proposal, not an adopted architecture decision or a new Alegor/Grafe implementation.

## Gource makes change visible, while Grafe must explain structure

Gource was more than a link in the inspiration list: the local research installed and ran **Gource 0.53** against GoCity’s 114-commit history and Algorithm Visualizer’s 668-commit history. The retained GoCity mid-frame makes its visual grammar concrete: a directory tree grows from the repository root, files appear as leaves, and contributor avatars accompany changes. The 640×360, 25fps export took about 24 seconds and emitted 426–427 raw PPM frames totaling roughly 294–295 MB; labels crowd at that small resolution. The Algorithm Visualizer export took roughly 30 seconds and emitted about 491 MB; a shallow one-commit input produced no useful history. These are **offline export observations**, not browser-performance measurements or a usability study. The local Gource version was 0.53; the official page now lists v0.56, so the experiment should not be represented as a current-version benchmark. ([Gource official site and releases](https://gource.io/); [run record](../../../experiments/grafe-reference-checks/gource-run.json); [retained GoCity frame](../../../experiments/grafe-reference-checks/gource-gocity-midframe.png))

The useful lesson is to borrow Gource’s *time controls and visual immediacy*, not to make its moving contribution tree the default architecture view. A file change does not prove that a function ran, a directory is architecturally important, or a relationship exists between two symbols. Grafe should keep a stable spatial map for orientation, let selection narrow the view to a readable neighborhood, and reserve animated replay for an **Evolution** mode that maps Git events onto the same stable locations. Every event should lead back to its commit and diff; contributor activity should be optional and never stand in for importance. Runtime paths belong in a separate layer and only after a real trace exists. This recommendation follows the Gource test limits and the earlier spatial-history study; the MVP does not yet provide this map/evolution experience. ([Spatial history research](../research_notes/Represent%20reference%20repository%20study/spatial-history.md); [Grafe research and test history](../grafe-research-and-tests.md))

The original Codevis reference is the project shown in the user’s Notion screenshot: `github.com/divan/codevis/cmd/codevis`. Its exact repository URL returned 404 on the research date, but that does not tell us whether it was made private, deleted, or moved. The author’s 2019 article describes an early alpha browser experiment using WebGL/Three.js, zoom-dependent relationships, and code shown when a concept could not be usefully decomposed; the author also calls out the difficulty of physics tuning and rendering many text lines. This is valuable design intent, not a usable source checkout or a validated UX result. Public KDE Codevis is a separate C++/Clang tool. Its documentation suggests transferable ideas—forward/reverse dependency depth, expandable covered nodes, details, and a viewport minimap—but it was reviewed from documentation, not cloned or run. ([divan’s article](https://divan.dev/posts/visual_programming_go/); [unavailable original repository URL](https://github.com/divan/codevis); [KDE Codevis guide](https://github.com/KDE/codevis/blob/main/doc/getting_started.md); [Grafe reference screenshot](../../../experiments/grafe-reference-checks/notion-codevis.png))

For Grafe, the recommended interaction contract is three levels: **overview** locates packages, folders, files, and major symbols; **focus** shows a selected symbol’s callers, outgoing relations, references, and tests; **detail** opens its exact path, line, snippet, relation type, and evidence status. A minimap should show the current viewport and selected area, follow navigation by default, and allow the user to unpin it. Keep a list or outline for dense areas, label candidates and unknowns, and distinguish physical placement from semantic links. The current MVP is strongest at focus and evidence: bounded TypeScript/JavaScript indexing, typed relations, source excerpts, search, evidence, and manual snapshots. It does not yet implement the project-wide map, detachable minimap, Gource-like playback, IDE cursor sync, 3D space, or runtime tracing. The exact pilot counts and limits are in the [Grafe dossier](../grafe-research-and-tests.md) and [MVP reference](../../reference/grafe-mvp.md).

The proposed companion has three modes. **Orient** restores project identity, recent snapshots, decisions, and a resumable pointer to the relevant tool or task. **Make** turns a user goal into a bounded plan, shows which project/snapshot and permissions it will use, and acts within standing project-scoped capability grants. It asks for confirmation only when a job needs new access, an unapproved write or destructive action, spend beyond its budget, or an external side effect; it then returns a visible artifact such as a graph view, comparison, patch, or report. **Follow up** is user-enabled monitoring of a chosen project signal or task; it shows what it checks, when it last ran, its resource/time budget, and controls to pause, stop, or cancel. Optional voice can come later as another way to interact with these same modes. These are proposed future behaviors, not current Alegor features; the existing MVP remains a deterministic Git/docs timeline and citation tool. This research **does not implement or enable new AI behavior**. Any future model calls still route through Ghost, and any write-capable or scheduled action needs explicit scope and controls.

The existing **Alegor MVP is a foundation, not the proposed companion shell**: it captures bounded Git history and selected Markdown documents, presents dated comparisons and citations, and currently makes no model calls or autonomous changes. The static restart prototype at port 8872 and the current MVP at port 8874 are different artifacts; the old prototype should not be mistaken for a working “Represent OS.” No shared login, cross-tool deep-link contract, conversational agent, job control plane, or compute runtime has been implemented. Keep the name **Represent Workspace** for the user-facing shell and reserve **Represent OS** as an internal metaphor unless research shows users understand it; “OS” can otherwise imply a new operating system distribution. Alegor can name the companion role under the Represent suite. These are naming recommendations, not locked brand decisions or a domain/trademark check. ## A desktop-like web shell needs no container at first

Separate four concerns that the “computer” metaphor can blur: the **workspace UI** presents projects, apps, artifacts, history, and task status; the **control plane** owns identity, permissions, snapshots, jobs, budgets, and audit evidence; the **execution plane** runs a narrowly scoped task when needed; an optional **remote desktop** streams a general-purpose GUI only for workflows that need it. These are logical boundaries and need not be four services in the first build. Right now Grafe and Alegor read bounded project evidence but do not execute target-project scripts, so a container adds setup and lifecycle without serving their current workflow. ([Alegor core](../../../src/alegor/core.mjs); [Grafe core](../../../src/grafe/core.mjs); [Represent OS runtime research](../research_notes/Represent%20OS%20design%20and%20runtime/runtime.md))

| Option | What it gives Represent | Recommendation |
|---|---|---|
| Web workspace with existing local services | Project home, app launcher, artifact pane, timeline, evidence, task status | **Build this first.** It needs no Linux VM or container to open Grafe/Alegor snapshots and Represent artifacts. |
| Connected local runner | Access to the user’s selected files, local tools, or IDE | Add only when a real task needs it; show folder scope and separate read/write and command permissions. It runs with local-user authority and is not a hostile-code sandbox. |
| Browser JS runtime | Fast browser-only JS/Node demo or preview | Optional narrow experiment; it does not replace a general Linux build/test environment. |
| Disposable local container | Reproducible Linux command environment for a one-off build/test | Use for a measured developer spike after choosing an actual command. Bound resources/time/network and operate on a disposable copy. Rootless mode can reduce some daemon risks but has limitations; it is not a blanket safety guarantee. |
| Managed hosted sandbox or microVM | On-demand remote code execution with provider lifecycle and isolation features | Compare providers only when a hosted use case exists, using the same task and workload measures. Keep durable job records and outputs outside the ephemeral runtime. |
| Self-operated gVisor/Firecracker fleet or full desktop VM | Control over a specialized execution platform or GUI session | Defer. It brings runtime, image, network, security, lifecycle, storage, and incident-response operations that current Represent tools do not need. |

A container packages a process and shares its host kernel; a VM runs a separate kernel. A Linux container does **not** need a desktop, window manager, or remote screen: a command runner needs an image, filesystem, process boundary, and defined inputs/outputs. Rootless containers can reduce some daemon risks, while gVisor and Firecracker offer different isolation models with their own compatibility or operations costs. On this Windows workstation WSL2/Docker were only checked for availability; no container or runtime was started. Windows local use adds Docker Desktop/WSL2 setup and Linux-VM lifecycle to the developer experience, so it should solve a real reproducibility need before becoming a prerequisite. No provider was provisioned, tested, or costed for a Represent workload. If Represent later executes untrusted repository code for multiple users, “we use Docker” is not a sufficient boundary: use a hardened per-task sandbox or managed microVM, scope filesystem and network access, cap resources and duration, keep credentials in the control plane, and preserve outputs outside ephemeral compute. ([Docker container/VM distinction](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/); [Docker security](https://docs.docker.com/engine/security/); [rootless mode](https://docs.docker.com/engine/security/rootless/); [gVisor](https://gvisor.dev/docs/); [Firecracker](https://firecracker-microvm.github.io/); [OpenAI sandbox security guidance](https://developers.openai.com/api/docs/guides/agents-api/environments/security))

### A minimal Linux image is a later tool, with real lifecycle costs

If a first task needs a reproducible Linux build/test environment, start with a **small Debian-based image** and add only the needed tools. The official Node image notes describe Alpine as roughly 25% smaller for a cited image comparison, but Alpine uses musl rather than glibc, some glibc software does not work on it, and the Node musl build has experimental-support caveats; common tools such as Git and Bash are also absent from minimal variants. That is a compatibility tradeoff, not a Represent benchmark. Prefer Alpine only if image transfer/startup measurements matter enough to justify package compatibility work. ([Official Node Docker image guidance](https://github.com/nodejs/docker-node))

For a hosted pilot, **Cloudflare Sandbox and E2B are reasonable candidates to compare**, not a vendor choice. The 2026-10-21 research snapshot of Cloudflare’s docs lists a $5/month Workers Paid plan with included compute, memory, and disk allowances, then separate billing dimensions for active CPU, provisioned memory, disk, egress, Worker and Durable Object use. An idle sandbox can still consume provisioned memory/disk until stopped, and its instance files do not become durable project history automatically; Cloudflare documents external persistence options and snapshot limits. E2B’s page at the same research date describes running sandboxes billed per second, with compute rates by vCPU and memory and separate storage terms; its listed Hobby credit/limits and Pro base price are plan-specific and can change. Neither figure is a total estimate for Represent: duration, memory, disk, regions, egress, concurrency, idle lifecycle, and provider-plan eligibility affect spend. Recheck official billing pages before any trial and measure one representative task end to end. ([Cloudflare Containers pricing](https://developers.cloudflare.com/containers/pricing/); [Cloudflare billing dimensions](https://developers.cloudflare.com/billing/understand/how-charges-accrue/); [Cloudflare persistence and lifetime](https://developers.cloudflare.com/sandbox/concepts/lifetime/); [E2B pricing](https://e2b.dev/pricing))

### One end-to-end task can test the proposed product

Imagine a developer returns to Plane Sync and asks, “What calls `upsertImpl`, and what should I review before changing it?” **Orient** opens the right project, branch, and saved snapshot, then links to Grafe’s confirmed callers. **Grafe** shows the production call sites and keeps the five dynamic-import test-name mentions marked as candidates, with exact source lines; it does not claim those candidate tests prove runtime coverage. **Make** offers a bounded plan: inspect those callers and tests, optionally run a named test command on a disposable copy, then produce a source-linked impact report and updated graph artifact. The task runs within an existing project-scoped grant, or asks for confirmation if it introduces a new access scope, write/destructive action, over-budget spend, or external side effect. Stop/cancel controls stay available throughout. Alegor records the resulting artifact against the source snapshot. **Follow up** can be enabled to check for later changes to those paths and report them under a stated cadence and budget. Today only the captured Grafe/Alegor evidence workflow exists; command execution, shared artifact identity, approvals for newly introduced scopes, scheduled checks, and companion modes remain proposals. This scenario adapts the actual Plane Sync pilot, where `upsertImpl` resolved to three production callers and five dynamic-import test mentions were candidates. ([Grafe real pilot](../../../experiments/grafe-mvp/README.md); [Alegor real pilot](../../../experiments/alegor-mvp/README.md))

Interactive generated work also creates a separate browser-preview boundary. A compute sandbox does not isolate HTML loaded into the main app’s origin. Prefer structured data rendered by trusted Represent components; if later previewing arbitrary HTML/JS, serve it from a separate origin in a narrowly sandboxed iframe with a small typed message bridge. This is a forward-looking recommendation, not a current Grafe/Alegor feature. ([MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy); [MDN iframe sandboxing](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/General_embedding_technologies); [MDN `postMessage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage))

## System Intent

Explore a project-centered Represent workspace that makes current project identity, snapshots, tasks, and interactive Represent works easy to reopen. Within it, Grafe answers “where is this code and how is it connected?”, Alegor answers “what changed and what was I doing?”, and Visu can later provide a living illustrated overview when that track resumes. The research asks how to use Gource, Codevis, Dot, Skales, and runtime references without confusing visual inspiration, product documentation, implementation evidence, and tested behavior. It does not authorize or describe a new implementation phase.

## Ingestion Vector

Research sources are bounded to the existing Represent docs and MVPs, the user’s original Notion notes and supplied screenshot, reference artifacts, and the cited primary vendor/project documentation. A future Workspace prototype should make its own bounded project sources explicit:

```text
project-root/
├── README.md                 # @LLM-ENTRY: project purpose and vocabulary
├── docs/                     # @LLM-TARGET: declared design, tasks, and status evidence
├── src/                      # @LLM-TARGET: code structure and source-linked relations
├── .git/                     # @LLM-TARGET: revision identity and change history
├── public/                   # @LLM-DECORATIVE: owned visual identity and style evidence
├── package.json              # @LLM-TARGET: languages, scripts, and package boundaries
├── node_modules/             # @LLM-IGNORE: installed third-party dependencies
└── dist/                     # @LLM-IGNORE: generated output by default
```

The tree is a proposal, not a scanner contract. A real onboarding flow should preview included/excluded paths and let the user correct scope before capture. Personal assistant transcripts, secrets, ignored/generated data, and arbitrary commands are not assumed inputs.

## Bootstrapping Steps

1. Treat this report and infographic as a research recommendation only. If the owner accepts the direction, record a separate architecture decision and scope an integrated workspace tracker; do not silently convert this proposal into current-state documentation.
2. Draw the shell around existing Grafe and Alegor URLs/artifacts using a project switcher, recent snapshot list, app launcher, and evidence/task pane. Keep each tool operable independently and make deep links preserve project and snapshot identity.
3. Run one re-entry task with multiple clearly labeled projects and snapshots. Measure whether a person can select the right project, explain its latest change from citations, and reopen the correct Grafe view without confusing branches or sessions.
4. Prototype Grafe’s overview/focus/detail contract against a fixed larger code scope. Measure source-link correctness, relation certainty, task completion, density, and time; separately prototype Gource-like playback from Git events on a stable layout.
5. Only after identifying a command the workspace should run, compare local execution and one disposable sandbox on the same public/sample project. Record cold start, task time, compatibility, resource use, network policy, cancellation, cleanup, and artifact export. Do not infer multi-tenant safety from a local test.
6. Test the artifact-preview origin boundary separately from the compute runner before accepting executable previews. Keep manual snapshots and avoid automatic paid model work until scope, need, and cost are supported by measured evidence.

## Ghost AI Plan

Represent’s locked rule remains: AI calls go through Ghost’s AI pipeline. The present Grafe and Alegor MVP flows described here use no model calls, and this report does not implement or enable new AI behavior. If an Alegor companion later synthesizes project status or chooses explanations, give each output source snapshot/evidence digests and prompt/model version in its cache key, cite the captured source, expose uncertainty, and make refresh explicit. Viewing saved evidence should be free of new inference calls. Keep execution credentials and model-provider secrets outside any sandbox; do not connect a runtime provider directly to a future tool UI.

## Embeddability Plan

Keep the workspace’s project model, snapshot IDs, evidence ledger, task records, and artifact links in a headless service/library contract. The first web shell should be a thin composition of the existing tools, not a rewrite or an OS image. CLI/library access remains available; later VS Code, JetBrains, desktop, and mobile surfaces can open the same project/snapshot and artifact IDs. Any local connector or remote runner should be an adapter behind a narrow job interface, so web, IDE, and desktop surfaces do not own execution semantics. Keep remote desktop streaming as a separate adapter for a proven GUI workflow, not a prerequisite for embedding the tools.

## Conclusion

Represent can borrow the *legibility* of Gource and Dot while keeping their distinct jobs separate: Gource makes change move through time; Grafe must prove code relationships; Dot shows a companion beside a computer, while Represent should show a companion beside project work. Skales contributes documented workflow ideas but no source reuse or app-tested claims. The product’s leanest next architecture is a web workspace over real project artifacts, with an optional, explicit compute adapter for tasks that need execution.

An open-source community can start with useful, composable work even if a hosted service never makes economic sense: publish versioned evidence and artifact schemas, extractor/runner adapter contracts, small sanitized fixtures, correctness and coverage reports, and reproducible task recipes. These are proposed contribution entry points, not evidence of demand; repository stars do not establish active use, willingness to contribute, or product fit. Existing developer-needs research explicitly identifies these as hypotheses and lists the validation gaps. ([Developer needs evidence](../research_notes/Represent%20parallel%20track%20restart/developer-needs.md))

The decisive trigger for adding Unix compute is concrete: a validated Represent task must run code or tools that the existing local services cannot run safely or reproducibly. Until then, investing in project/snapshot identity, artifact navigation, and a re-entry test teaches more about the product than provisioning a VM. Any later runtime trial should be an isolated, measured experiment and remain separate from the user-facing desktop metaphor.
