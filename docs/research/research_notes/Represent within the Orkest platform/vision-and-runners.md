# Represent within the Orkest platform: vision and runners

Research date: 2026-10-21. This note compares the earlier “Represent OS” proposal with the operator's clarified Waremoto direction and the current Orkest/Ghost design. It treats the attached “Runner VM and verify sandbox” passage as context from another active session, not as approval to provision, change, or implement any runtime. The task is research and recommendation only; no code, infrastructure, credentials, or Orkest/Ghost decisions were changed.

## How does the earlier Represent proposal compare with the operator's wider platform vision?

### Takeaway

The earlier proposal is still useful as a presentation and product-UX hypothesis, but it put too much product responsibility inside Represent. The clarified direction is broader: Maremoto is the company strategy, Orkest/Ghost is the agent work platform, and Represent is a specialist AI-dev-tooling branch that can create focused products and tools; Visu, Grafe, and Alegor are possible work surfaces inside that larger system. The next design should test Represent as an integrated specialist capability on Orkest, instead of assuming it needs to become an independent “Represent OS” with its own scheduler, identity system, agent runtime, and durable project store.

### Cited Findings

- Waremoto describes itself as the software department of Maremoto and Orkest as an AI-dev-focused programmer's cockpit and minimalist Jira; its product direction is to begin over Multica, then grow a standalone board, then support both modes. This makes Orkest a plausible platform host for specialized developer tools, while Represent can remain a product/tool family. [Waremoto project map](../../../../../CLAUDE.md); [Orkest CONTEXT](../../../../../orkest/docs/CONTEXT.md)
- Orkest's present system design separates responsibilities: Multica routes and displays agent work, Ghost records authority and verifies candidate work, and the operator approves. Its extraction seam is the WorkBoard / AgentRun / Identity contract set, with Multica and a future native board as implementations. [Orkest design](../../../../../orkest/docs/design/orkest-cockpit-and-multica.md); [Orkest reference](../../../../../orkest/docs/reference/orkest.md)
- Current implementation status is more limited than the future product vision: the Orkest cockpit fork and adapter are underway, but its runner VM, verify sandbox, and candidates remote are not built; Phase 4 waits on OQ-8 approval. No Multica daemon or agent may run before the containment gate. [Orkest CONTEXT](../../../../../orkest/docs/CONTEXT.md); [ORKEST-FORK tracker](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md)
- Orkest's audited setup guide says CloudCLI is an external tool with its own login, is not embedded or in platform mode, and is being studied for session readers. It also says Orkest's planned unattended path uses dedicated provider keys and does not put subscription logins in its runner VM. [Multica and CloudCLI guide](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md)
- Represent already has working local tools, not just a concept: Visu creates source-grounded illustrated overviews; Grafe explores bounded JavaScript/TypeScript relationships; Alegor captures Git/docs history and citations. The project context reports the three MVPs implemented, with Visu paused, and no public deployment or cross-tool snapshot interoperability claimed. [Represent CONTEXT](../../../CONTEXT.md); [Visu reference](../../../reference/visu-discovery.md); [Grafe reference](../../../reference/grafe-mvp.md); [Alegor reference](../../../reference/alegor-mvp.md)
- The previous “Represent OS design and runtime” report recommended a project-centered web workspace, Alegor as a companion, and optional compute attached to jobs. It explicitly described the infographic as static research, the runner as future work, and command execution / shared artifact identity / follow-up monitoring as proposals. [Earlier Represent OS report](../../../research/reports/Represent%20OS%20design%20and%20runtime.md)
- The supplied runner comparison lists tangible trade-offs: the isolated Linux runner reduces access to lab1 credentials and systems but costs maintenance, host resources and round-trip time; the verifier is slower and needs stack-specific environments but can test a commit the agent did not control. [User-supplied runner comparison](C:/Users/Administrator/.codex/attachments/bfc55e0d-41d3-4844-91a7-61093664edf9/Pasted%20text.txt) (local context file)

### Inferences

| Question | Earlier proposal | Clarified direction | What follows |
|---|---|---|---|
| What is the center of the product? | A Represent-owned project workspace / “OS” | A specialist AI-dev-tooling branch of Maremoto, fitting into Orkest/Ghost's agent workflow | Make Represent's capabilities and artifacts first-class inside the platform; keep a standalone path as an option, not the premise. |
| Who runs agents and owns work? | Future Represent service/control plane and optional runner adapter | Orkest/Ghost and the chosen board/runtime integration; Multica is the first board/executor layer in its current plan | Avoid inventing a second scheduler, provider bridge, task store, or permission system before an integration proof. |
| What are the tools? | Grafe and Alegor, with Visu deferred in that report | Visu is liked and can be one of the tools inside Represent; Grafe, Visu, and Alegor are specialist views | Present them as complementary tools, preserving their distinct evidence and project state. |
| What does “leaner Dot” mean? | Desktop-like web workspace with a companion and optional runner | A local developer product that connects to existing agent CLIs/subscriptions and gives a tailored interactive work surface | Aim for the experience/capabilities of a persistent companion beside a usable computer/workspace, not an attempt to reproduce Dot's private implementation. |
| What should be built next? | Draw a shell around current app URLs and snapshots | Start from Multica/CloudCLI learning and Orkest integration; identify where Represent adds unique developer value | Prove a project-aware handoff from Orkest to a real Represent view and back, preserving project/branch/snapshot/task identity. |

The earlier proposal was therefore too web-workspace-first and too conservative about the role of agent work. It assumed that simply opening existing tools in a desktop-like web UI was the most informative next step. The user's latest context says the key product question is whether Represent can become a focused, expert workspace on top of the tools and agent platform being shaped through Orkest and Multica. The earlier report still contributes useful ideas: evidence-backed views, visible project and snapshot identity, UI clarity, progressive detail, separate artifact-preview security, and a web interface that does not pretend to be an operating system.

“Recreate Dot” is a useful experience target: a persistent companion, a computer/work area visible beside conversation, continuity between sessions, and a clear way to inspect or take control of ongoing work. The supplied screenshot demonstrates those interaction ideas. It does not prove Dot's infrastructure, security model, agent orchestration, or whether its computer is a full VM. Represent should compete through a developer-focused workflow and its own tools, not clone hidden mechanisms.

“Open and simpler but expert” is a product thesis, not yet validated market evidence. A useful open contribution surface could be tool adapters, evidence/artifact schemas, project fixtures, source-link correctness checks, and orchestration integrations. This follows from the desire to build open tools and from the existing tool boundaries; it does not establish demand or sustainable economics.

### Gaps

- The Waremoto, Orkest, and Represent documentation do not yet settle whether Represent should be a separately distributable product, a set of Orkest panels/plugins, or both. The user has described both specialist products and platform integration as possibilities.
- The exact Multica + CloudCLI setup being assembled in the user's current Claude Code session was not inspected from runtime state. The setup guide is an audited design/knowledge record, not proof that all future Orkest paths exist or that CloudCLI provides full provider parity.
- No product interview, customer evidence, usage data, or external market sizing was used. “Open and simpler but expert” should remain a hypothesis until tested with developers beyond the operator.
- This note does not change the current Orkest decisions or authorize the proposed runner infrastructure.

## What should Represent own, and what should it reuse from Orkest, Ghost, Multica, CloudCLI, and the existing tools?

### Takeaway

Represent should own the specialist developer value: code/project understanding, visual explanations, and links between those explanations and the work being done. Orkest/Ghost should remain the candidate owners of task orchestration, identity, agent dispatch, run limits, acceptance receipts, and human decision flow. Multica and CloudCLI are learning/reference systems and possible integrations; their audited role and licensing constraints do not imply source reuse, platform embedding, or feature parity. Prove a narrow handoff using the current tools before designing another general companion platform.

### Cited Findings

- Orkest's documented role is the programmer's cockpit and GhostDev workflow, with Multica as the initial board/agent-run layer. Multica statuses are routing/display information, not trusted verification; Ghost's record, an independent receipt, and operator approval establish accepted work. [Orkest design](../../../../../orkest/docs/design/orkest-cockpit-and-multica.md); [unattended work reference](../../../../../orkest/docs/reference/unattended-work.md)
- The guide documents CloudCLI as a separate session product with its own login and a Phase 5 study target for reading Claude Code, Codex, Cursor CLI, and OpenCode sessions. It explicitly separates session reading from launching/resuming code and cautions that listed readers do not establish complete lifecycle parity. [Multica and CloudCLI guide](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md)
- The same guide records Orkest's policy not to copy Multica's source/UI/assets into first-party code, and to reimplement desired ideas and workflows. It describes CloudCLI as AGPL and outside the platform; future distribution or hosted plans should recheck the exact license and deployment relationship. [Orkest design](../../../../../orkest/docs/design/orkest-cockpit-and-multica.md); [Multica and CloudCLI guide](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md)
- Current Represent tools have separate evidence domains and functions. Visu uses bounded source documents and Ghost for its optional story/art workflow; Grafe statically indexes bounded JS/TS source; Alegor stores bounded Git/docs snapshots and citations. None of their current MVP descriptions claims to dispatch coding agents or execute arbitrary project commands. [Visu reference](../../../reference/visu-discovery.md); [Grafe reference](../../../reference/grafe-mvp.md); [Alegor reference](../../../reference/alegor-mvp.md)
- The prior design separated workspace UI, control plane, execution plane, and optional remote desktop, while acknowledging these could start in fewer processes. It also recommended keeping current deterministic tools out of a container until a job needs project-code execution. [Earlier Represent OS report](../../../research/reports/Represent%20OS%20design%20and%20runtime.md); [runtime research note](../Represent%20OS%20design%20and%20runtime/runtime.md)

### Inferences

A plausible responsibility split to test is:

- **Represent:** specialist tool catalog and project visualization workflows; Visu/Grafe/Alegor; evidence-rich artifacts; shared project/snapshot/branch references; adapters that can expose these tools to more than one host.
- **Orkest:** developer cockpit and task/workflow integration, initially using Multica's board/run facilities and retaining an adapter seam for a future native board.
- **Ghost:** platform control and authority where already designed: policy, dispatch/Foreman, persistent records, verification, reconciliation, and human-approved promotion.
- **Multica / CloudCLI:** external tools to integrate with, learn from, or replace capability-by-capability according to Orkest's staged product plan. Avoid treating a visible feature as proof of a trusted backend or a complete interface.

This is a division-of-responsibility hypothesis, not an approved architecture. The most useful first integration experiment appears to be a single, inspectable handoff: open a real Orkest task for a selected repository; launch Visu, Grafe, or Alegor with the exact project and captured revision; return a stable artifact link and evidence summary to the task; and preserve clear status about what was captured, inferred, executed, and independently verified. That tests whether Represent adds practical expert value inside the flow without cloning Orkest's agent runtime.

The integration contract should avoid assuming one common “project snapshot” format prematurely. Today the tools use distinct source scopes and persisted formats, and interoperability is not claimed. First establish identifiers for project, Git revision / worktree, tool artifact, source evidence, and task/run; then learn which fields must be shared. Keep product-specific visual artifacts independent where their schemas differ.

Alegor's previous proposal framed it as a conversational three-mode companion (Orient / Make / Follow up). That is an interesting long-term UX direction, but the ownership map suggests the “Make” and autonomous follow-up parts could duplicate Orkest/Ghost scheduling and agent control. Alegor can instead start as a Represent project/history/evidence lens, with a deep-link and handoff to Orkest for work. A later companion can sit above both, only if user testing shows the split is awkward.

Visu should be framed as one of Represent's tools, not the identity of the whole platform and not permanently excluded from the suite. User likes its “memorable overview” output and it already produces an illustrated overview workflow. Whether it remains paused for code work is a scheduling choice; its product role can still appear in the suite model and future Orkest launch surface.

### Gaps

- No adapter or API contract currently proves that Orkest can deep-link into Visu/Grafe/Alegor and return an artifact while preserving source/task identity.
- It is unclear whether the user's Multica-coupled Orkest experiment will use Multica as an install dependency, a remote service, an API adapter, or multiple modes; the docs describe intended stages, not the exact active experiment.
- The interaction between Orkest's future session readers, CloudCLI's local session data, and Alegor's project history is not designed. Session access, resume, and command execution must be treated as distinct capabilities.
- Provider subscriptions, token handling, and local CLI authentication differ by tool and provider. No new auth topology is recommended here; the existing Orkest runner design explicitly excludes subscription logins and needs its own operator-approved isolation path.

## How should the runner and verify boundaries work, and is a minimal Unix container enough?

### Takeaway

There are two independent boundaries, serving different trust jobs. A long-lived runner hosts an agent that writes candidate code; a fresh verify environment executes that candidate code and checks an exact commit outside the agent's control. Do not combine the agent and verifier, and do not treat “a Docker container exists” as a security argument. For Represent's current read/visualization workflows, neither boundary is needed; for Orkest's designed unattended coding flow, the current plan calls for a separately isolated runner VM and disposable verifier, subject to the still-open OQ-8 approval and containment gate.

### Cited Findings

- Orkest's tracker states that no agent-authored code executes on lab1. The Multica agent runs only in the isolated Linux runner VM; candidate builds/tests run only in a disposable verification sandbox. The VM and sandbox have separate credentials and network allow-lists, and AC-10a containment probes must pass before any daemon/agent runs and whenever an allow-list changes. [ORKEST-FORK tracker](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md)
- The planned verifier resolves the candidate SHA, fetches it with a read-only credential, and runs Ghost-chosen checks in a disposable VM or container with no host drives, lab1 secrets, push credential, Docker, NATS, or lab1 loopback reach. Lab1 receives result artifacts as untrusted input and does not execute them. [Orkest design: verifier](../../../../../orkest/docs/design/orkest-cockpit-and-multica.md); [Orkest reference](../../../../../orkest/docs/reference/orkest.md)
- The design does not claim that an arbitrary container is sufficient. Its isolation list includes network limits, credentials, host-drive separation, Docker/NATS separation, a read-only verify key, bounded artifacts, and probes. It specifically rejects one VM for both runner and verifier because an agent-controlled machine cannot independently establish the result. [ORKEST-FORK tracker](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md); [user-supplied runner comparison](C:/Users/Administrator/.codex/attachments/bfc55e0d-41d3-4844-91a7-61093664edf9/Pasted%20text.txt)
- Orkest's audited Multica model says agents on one daemon share its OS user, home directory, daemon environment, and CLI logins; per-task work directories prevent collisions but are not a security boundary. Multica itself has no sandbox. The planned VM is the boundary because the daemon/agent identity is treated as compromised by design. [Unattended work reference](../../../../../orkest/docs/reference/unattended-work.md)
- The current implementation state says the Orkest runner VM, verify sandbox, and candidates remote are not built; OQ-8 approval is still a gate. The attached text is a comparison of pros/cons and recommendation, not evidence of approval or provisioning. [Orkest CONTEXT](../../../../../orkest/docs/CONTEXT.md); [ORKEST-FORK tracker](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md); [attached text](C:/Users/Administrator/.codex/attachments/bfc55e0d-41d3-4844-91a7-61093664edf9/Pasted%20text.txt)
- Docker's official documentation distinguishes containers, which share a host kernel, from virtual machines with a separate operating system/kernel, and documents that daemon access and host mounts materially affect security. Rootless mode reduces some risks but has documented limitations. [Docker containers and VMs](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/); [Docker Engine security](https://docs.docker.com/engine/security/); [Docker Rootless mode](https://docs.docker.com/engine/security/rootless/)
- The older Represent runtime note found that current Grafe and Alegor don't execute target-project code; it recommends no execution service for their present deterministic jobs and a later on-demand adapter for validated tasks. This finding is consistent with the checked-in MVP references. [Runtime research note](../Represent%20OS%20design%20and%20runtime/runtime.md); [Grafe reference](../../../reference/grafe-mvp.md); [Alegor reference](../../../reference/alegor-mvp.md)

### Inferences

Keep these concepts distinct:

| Boundary | Purpose | Lifetime | Trust relationship | Container/VM implication |
|---|---|---|---|---|
| **Agent runner** | Runs the coding agent, its CLI, task worktree, tools, and provider/runtime connection | Long-lived daemon with per-task workspaces and possible resumable sessions | Agent output and workspace are untrusted; runner may hold credentials and can affect its own environment | For the current Orkest plan, a Linux VM is the isolation boundary. A small Linux image can reduce maintenance but does not, by itself, solve same-user shared access or host reach. |
| **Independent verifier** | Builds/tests an exact candidate SHA and returns a bounded receipt | Fresh/disposable per verification (with controlled caches outside candidate control) | Agent cannot alter the verifier, checks, credentials, or acceptance record | Can be a hardened disposable VM or a container with a proven isolation envelope. Separate identity, read-only candidate access, network policy, trusted check definitions, and artifact parsing matter. |
| **Represent local analysis** | Captures source, builds graph/history, composes an overview | Local deterministic process | Current bounded readers do not run project code; source still needs path/symlink/size constraints | No sandbox needed for the existing read-only tools solely to present a desktop-like UI. |
| **Remote desktop** | Exposes a complete GUI computer for tasks that genuinely need it | Session-like, possibly persistent | Broad, general-purpose interaction surface | Highest lifecycle and attack-surface cost; not required merely because the UI resembles an OS. |

A “minimal containerized Unix environment” can be appropriate as an **execution packaging choice**, especially for an isolated verifier job or a local reproducible task. It is not automatically the right **agent runner architecture**. A Multica daemon is long-lived, starts multiple providers/agents, shares identity and state across tasks, and has a control-plane relationship; a disposable container intended for one test command is not equivalent. If a local CLI subscription session is to run inside a container/VM, prove its login persistence and provider terms, secret exposure, egress, cancellation, cleanup, resource limits, and cross-task separation rather than assuming the developer's local auth can safely be mounted into it.

For the user's “leaner Dot” target, the initial design need not have a full OS image or streamed desktop. A Represent/Orkest work surface can show project files, interactive Visu/Grafe/Alegor tools, conversation, tasks, logs, and review state in a web UI. A real terminal or GUI computer should appear only when backed by an execution adapter with explicit state, ownership, and lifecycle. The interface may feel like a tailored computer without claiming that a Linux environment is running behind every view.

The old Represent report's phrase “add an on-demand execution adapter when a validated job needs code execution” remains sound; its apparent implication that runner architecture should be deferred until a Represent command appears is too narrow in this cross-platform context. Orkest already has a distinct unattended coding use case and a security design. Represent should consume or integrate with that platform boundary if its tools need to trigger coding work, not design a competing runner. Conversely, the Orkest plan does not imply that every Represent reader, infographic, or visualization should execute in a VM.

The correct next architecture proof is a **platform integration trace**, not immediate infrastructure provisioning: map one selected developer task end-to-end across Orkest, Multica, Ghost, and a Represent tool; identify which existing service owns dispatch, agent credentials, run status, verification, artifacts, and approval; mark which steps are implemented, planned, or gated; then demonstrate a read-only or otherwise already-authorized Represent handoff that returns source-linked artifacts. Only when that trace requires a new capability should the relevant runtime question be opened in its owning tracker.

### Gaps

- OQ-8 remains unapproved in the current tracker. This report is not an approval and makes no resource/provisioning recommendation for a specific VM instance.
- The exact runner VM and verifier image, cache persistence, Windows/Unity strategy, and cross-project concurrency are still design or spike questions. The user-supplied note outlines trade-offs but does not settle them.
- The existing Orkest docs describe a Linux runner first and flag Unity/Windows needs as a separate later runtime question. This note does not revise the OQ-8 scope or decide multi-OS runners.
- No containment probes, workload benchmark, local container job, or VM task was run for this report. Docker documentation describes generic mechanisms; it does not prove that any selected local setup meets Orkest's AC-10a requirements.
- The user said their current Claude Code session is deciding how to work with unmanaged code in Orkest and Multica. Its complete thread was not read; the attached runner note was treated only as context.
