# Represent within the Orkest platform and company stack

Research note prepared 2026-10-21 for comparing the prior Represent-centered “OS” proposal with the operator’s Maremoto / Orkest direction. This is an internal-source synthesis, not a new architecture decision. Repository heads inspected: umbrella `D:/ware` `132edce`, Ghost `e3e02027`, GhostDev `6027378`, Orkest `f0bcd86`, Represent `2381ac2`. The company docs disagree in places and the distinction between designed, implemented and deployed is preserved below.

## 1. Who owns which layer, and what does Represent mean in that map?

### Takeaway

Treat **Maremoto** as the company, **Waremoto** as its software organization, **GhostWare** as reusable runtime infrastructure, and **Orkest** as the emerging AI development work platform. Place **Represent** as the Maremoto/Waremoto product line for making software projects legible, with Visu and Grafe as product views and Alegor as a project-context companion or module. “Represent branch” can describe a product portfolio or studio inside Maremoto; the canonical taxonomy does not currently define a separate corporate branch or division, so avoid silently turning it into a new legal or repository hierarchy.

### Cited Findings

- The canonical taxonomy distinguishes Maremoto SpA (legal entity), Maremoto (company brand), Waremoto (software department) and GhostWare (shared runtime); Waremoto is the “house,” while GhostWare is infrastructure. The taxonomy also explicitly allows standalone Waremoto products without a Ghost prefix. [Naming & Branding, lines 9–27](../../../../../docs/reference/naming-and-branding.md#L9-L27)
- That same document describes GhostDev as methodology and AFK dispatch under one product brand, and lists Represent among out-of-family products. Its header says the naming document began as a plan, but it also records completed rename phases; therefore it is useful for taxonomy, while the current project state should come from each project’s living context. [Naming & Branding, lines 3–4, 46–56, 68–82, 159–166](../../../../../docs/reference/naming-and-branding.md#L46-L56)
- The current Represent context says the repo is the suite root for multiple visualization modes, ingestion strategies and output surfaces; it currently has Visu, Grafe and Alegor local MVPs. Visu is paused, and Grafe/Alegor are separate continuing tracks. [Represent CONTEXT, lines 7–37](../../../CONTEXT.md#L7-L37)
- The user’s newer company direction differs from the older company vision’s “first commercial product” framing. The older vision describes Represent as a code-visualization product and cites creatures/cities, static analysis and runtime overlays; the current Represent context records “A memorable overview,” style detection, on-demand detail, and three concrete tools. [Maremoto Vision, lines 22–57](../../../../../docs/maremoto/maremoto-vision.md#L22-L57); [current Represent direction, lines 13–23](../../../CONTEXT.md#L13-L23)
- GhostDev already has a working methodology data plane for `/roadmap` and `/sessions`, built from the Represent adapter. Its current context calls this methrep, not the new Represent apps. [GhostDev CONTEXT, lines 16–24](../../../../../GhostDev/docs/CONTEXT.md#L16-L24)
- The older root product brief describes a broad “Represent” platform with scene graph, Unity renderer, runtime animation, and methrep integration. The current Represent context explicitly labels old design checkpoints as historical and records the working JS/TS, Git/docs and web MVPs instead. Do not use that old brief as the current implementation contract. [Historical product brief, lines 1–20](../../../../../docs/products/represent.md#L1-L20); [current Represent decisions and supersession, lines 33–64](../../../CONTEXT.md#L33-L64)

### Inferences

- A useful portfolio description is **“Maremoto’s AI developer-tools line”** or **“Represent, the project-understanding product family.”** This gives the user’s “branch” idea a place without confusing it with Waremoto (the department), GhostWare (infrastructure), or a new company entity. This is a recommendation, not a name already approved in the taxonomy.
- The product family should have composable tools: **Visu** makes the project’s important structure memorable; **Grafe** follows concrete code symbols and relationships; **Alegor** helps a person or agent recover project context and activity. They can share project identity, evidence references and snapshot lineage, while each reader stays replaceable.
- The boundary with GhostDev should be explicit. GhostDev owns methodology / IMPL state and its own cockpit data plane; Represent can visualize that data through a connector, but should not become a second authority for tracker status or promotion. A connector can make Represent views useful inside Orkest/GhostShell without moving source-of-truth ownership.
- The earlier proposal’s “Represent OS” was too broad as a product architecture. It combines a shell, a companion, visuals, project history and code exploration, all capabilities already split among GhostShell, Orkest, GhostDev and Represent. Keep “OS” as a user-interface metaphor if it tests well; do not let it imply a new kernel, desktop, agent runtime or competing project database.

### Gaps

- The canonical docs do not define an internal “AI developer tooling branch” within Maremoto or settle whether Represent is the umbrella brand, one product, or both. The user’s latest framing should be recorded as the new direction when the living docs are next reconciled.
- No human evaluation has yet established whether a single Represent workspace should host all three views or whether Orkest should own the top-level navigation. Current docs describe the suites and local apps, not an accepted cross-product information architecture.

## 2. Is Orkest the platform, and how is it different from GhostShell, GhostDev and a Represent workspace?

### Takeaway

The operator’s Orkest-first hypothesis fits the documented strategy better than making Represent a separate “OS.” Orkest is explicitly planned as a programmer’s cockpit that starts over Multica, grows a native board, then keeps both modes. But this is still a staged product with unfinished execution phases: call it an **emerging platform direction**, not a completed general agent platform. GhostShell is the existing Waremoto operator shell; GhostDev remains the process harness and judge; Represent supplies project-understanding views.

### Cited Findings

- Orkest’s living context says it is an AI-dev-focused minimalist Jira plus programmer cockpit, and its product direction is three stages: layer over Multica, build a standalone board that can replace Multica, then support both. The same context has locked decisions for product ownership and replaceable WorkBoard / AgentRun / Identity contracts. [Orkest CONTEXT, lines 10–20, 37–46](../../../../../orkest/docs/CONTEXT.md#L10-L20)
- Current Orkest product docs say the fork begins as a copy of the GhostDev cockpit; Multica supplies the board and AFK agent execution; Ghost supplies eligibility, SHA-bound verification receipts and operator approval. The adapter boundary is designed to keep Orkest extractable. [Orkest/Multica design, lines 14–22](../../../../../orkest/docs/design/orkest-cockpit-and-multica.md#L14-L22); [Ghost ORKEST-FORK, lines 505–509](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md#L505-L509)
- The current fork’s code and some evidence still live in Ghost, while Orkest has its own product-doc repository. The Ghost tracker calls the fork destination `layers/orkest` and says that extraction follows the adapter and layer boundaries. [Ghost ORKEST-FORK, lines 470–470, 505–509](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md#L470-L470)
- Orkest implementation status must be read across conflicting records. The Ghost tracker, updated 2026-10-21, marks cockpit fork Phase 2 done with operator approval and records adapter phases 3.1–3.3 done; the Orkest CONTEXT component table still says “Ready to start”; its tracker header also has a stale “Nothing is implemented” statement. The unattended-work doc says the fork is done and no agent has run. Treat the detailed phase evidence in the Ghost tracker as the strongest current status, and reconcile the stale summary docs before making product readiness claims. [Ghost tracker, lines 6–15, 192–202, 263–286](../../../../../Ghost/docs/ORKEST-FORK-IMPL.md#L6-L15); [Orkest CONTEXT, lines 24–33](../../../../../orkest/docs/CONTEXT.md#L24-L33); [Unattended work, lines 1–15](../../../../../orkest/docs/reference/unattended-work.md#L1-L15)
- The Orkest/Multica agent loop and runner are still design/gated work: the Multica instance and adapter exist, but no Multica daemon or agent has run; the isolated Linux runner VM and separate verify sandbox are the planned containment boundary. [Unattended work, lines 1–15, 63–82](../../../../../orkest/docs/reference/unattended-work.md#L1-L15)
- GhostShell already is the unified Nuxt 4 app hosting Ghost products, with methodology, AI Gateway, extensions and embeddable surfaces. Its docs describe it as the Waremoto operator hub and document modular `/x/*` surfaces. [GhostShell reference, lines 1–16, 20–38](../../../../../Ghost/docs/reference/ghost-shell.md#L1-L16)
- GhostDev’s role is not just a shell: its product includes the methodology harness and AFK dispatch, and its adapters provide structured project/roadmap/session data. [Naming & Branding, lines 50–56](../../../../../docs/reference/naming-and-branding.md#L50-L56); [GhostDev CONTEXT, lines 16–24](../../../../../GhostDev/docs/CONTEXT.md#L16-L24)
- Orkest’s current distribution sequence is explicitly adapters-first; Multica is not mandatory forever, and its source/UI/assets are not to be copied into first-party modules. [Orkest setup guide, lines 20–28, 179–183](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md#L20-L28)

### Inferences

- **Recommended architecture:** Orkest owns work orchestration and the developer’s project/work cockpit; GhostWare supplies Maremoto’s runtime, policy, verification and internal service integrations; GhostShell remains the internal Waremoto-wide operations hub; Represent is a product family of visualization and project-context capabilities that Orkest can embed or launch.
- A Represent-like “workspace” can still be valuable as a focused destination inside Orkest: project overview, code map, history, evidence and connected work sessions. It should receive project identity, branch, run and session context via contracts rather than maintaining a parallel kanban, runner, identity system or acceptance ledger.
- GhostShell can host an internal Represent preview or link while product UX is being learned. Rebuilding another general shell on top of it now would duplicate navigation, project selection, themes, panels and session surfaces. If Orkest becomes an independently distributed product, it should own its end-user cockpit instead of requiring GhostShell as a runtime dependency.
- “Platform” should be earned in stages: begin with a focused cockpit and stable adapters; add independent board and execution providers as real use cases demand; keep verified acceptance and security boundaries explicit. Multica’s own board status is a routing signal, not proof that work is safe or accepted, per the current Orkest design.

### Gaps

- Orkest’s three-stage product strategy is decided, but the native board scope, future runner provider API and full standalone installation contract are still open. The current design preserves adapter contracts, but does not establish a finished public plugin ecosystem.
- The “unmanaged agents” phrasing needs a product definition. Current Orkest documentation separates Multica’s agent execution from Ghost’s authoritative eligibility, verification and acceptance; those trust responsibilities should not be collapsed into one broad “agent platform” claim.
- The Orkest context calls the product minimalist Jira plus cockpit, while the Ghost tracker ties it to GhostDev verification. Whether the eventual public Orkest can operate usefully without GhostDev’s authority layer is not yet specified.

## 3. Integration seams, model/auth boundaries and a standalone distribution path

### Takeaway

Reuse existing products through replaceable interfaces, not by making every external install depend on the private Waremoto stack. Keep Ghost integration first-class for internal dogfooding, expose standalone-compatible adapters for Orkest and Represent, and distinguish **Represent-owned model requests** from **provider CLI sessions/agent execution**. Those paths have different authentication, accounting and isolation guarantees.

### Cited Findings

- Represent’s current locked decision says LLM calls it owns go through the Ghost AI pipeline for routing, caching, rate limits/retries, cost accounting and fallback. Its code core is also required to stay headless and framework-agnostic for web, IDE, desktop, CLI and library shells. [Represent CONTEXT, lines 47–58, 79–104](../../../CONTEXT.md#L47-L58)
- Ghost documents two different AI paths: application `IChatClient` calls are routed through the AI gateway; agentic Claude CLI work can use its own OAuth and bypass the gateway. Gateway-attributed session work is a separate capability and is not a universal guarantee for every CLI. [Ghost AI system, lines 11–34, 72–80, 201–218](../../../../../Ghost/docs/reference/ai-system.md#L11-L34)
- Ghost’s gateway reference says gateway use is keyed, attributed and budgeted; it also explicitly treats direct CLI OAuth as a distinct auth mode. A gateway virtual key is not a general-purpose login for an attached CLI. [AI Gateway, lines 1–20, 723–745](../../../../../Ghost/docs/reference/ai-gateway.md#L723-L745)
- Orkest’s planned Multica runner uses dedicated provider API keys in its isolated VM; the design rejects LiteLLM virtual keys for that runner path. This is an operator decision for that execution environment, not evidence that all Orkest deployments must use those exact credentials. [Orkest setup guide, lines 146–157](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md#L146-L157); [Unattended work, lines 63–82](../../../../../orkest/docs/reference/unattended-work.md#L63-L82)
- Orkest proposes separate WorkBoard, AgentRun and Identity contracts, and its longer-run plan replaces Multica’s board with a native implementation while supporting both paths. [Orkest CONTEXT, lines 37–46](../../../../../orkest/docs/CONTEXT.md#L37-L46); [setup guide, lines 20–28](../../../../../orkest/docs/guides/multica-cloudcli-knowledge-and-setup.md#L20-L28)
- The current Represent MVPs are local apps with manual snapshots and no model calls. They do not claim public deployment, provider-session connectors or cross-tool snapshot interoperability. [Represent CONTEXT, lines 7–11, 33–37](../../../CONTEXT.md#L7-L11)
- WARE-ROOTS says Ghost/apps is frozen to new product entries and new apps/tools should live as top-level siblings with their own repositories, registered in `ware.json` or ignored. [WARE-ROOTS, lines 1–5, 11–22](../../../../../docs/reference/ware-roots.md#L1-L22)

### Inferences

- Define small contracts around **Project**, **Snapshot/Evidence**, **Visualization**, **WorkBoard**, **AgentRun/Session**, **Identity**, and **AI task execution**. Internal adapters can read GhostDev/methrep, GhostShell and Ghost services; external users can install local readers or point Orkest at their own board, runner and identity provider. The contract should carry provenance and explicit uncertainty so one product’s display never becomes another product’s source of truth.
- **For Represent-owned AI:** retain the locked internal route through Ghost’s gateway. To distribute Represent as open software without requiring Maremoto’s private deployment, the gateway capability needs a supported replaceable backend boundary: a locally deployable/open distribution of the compatible Ghost gateway, or a bring-your-own endpoint adapter with the same explicit policy/accounting semantics. Keep direct provider SDK code out of each visualization tool. The docs currently lock Ghost for the internal stack but do not yet specify the external installation contract.
- **For attached Claude/Codex/Grok tools:** treat authentication and execution as provider/session adapters running under their supported CLI login or explicitly supplied provider credentials. Do not claim those calls are governed by LiteLLM unless the session harness actually routes and attributes them through the gateway. If agents can write code, place them in an isolated runner environment and let a separate verifier and human approval gate decide acceptance.
- A layered adoption path fits the user’s “open, simpler but expert” goal:
  1. **Internal dogfood:** Represent tools may consume GhostDev/methrep data and Ghost AI gateway calls; Orkest can use Ghost’s policy/verification and current Multica adapter.
  2. **Open local core:** keep Visu/Grafe and evidence/snapshot formats usable on a repository without GhostShell, a private server, or an agent runner. Core/CLI and static views should still work offline.
  3. **Open work platform:** ship Orkest with supported integrations through interfaces; allow a customer’s existing Multica/board first, then an Orkest-owned board, and let execution adapters connect to their chosen agent runtime.
  4. **Optional managed service:** host coordination, storage or runner infrastructure only when users actually need it; preserve export, local-first modes and explicit data boundaries.
- An “OS-like” experience can be built as the web shell for Orkest or as a Represent project workspace module. The process/agent VM is an independent execution boundary, not the UI operating system. A lightweight web app plus local CLI/readers is the likely first product shape; disposable Linux VMs belong behind the agent-runner adapter when untrusted code execution is introduced.
- The previous “Represent OS” proposal therefore has useful pieces—project-centered navigation, persistent context, history, connected tools, optional runners—but assigns them to an overly broad new system. Keep the visual project experience in Represent; let Orkest own the cockpit/work routing; use GhostShell as Waremoto’s internal home; use GhostWare as internal runtime infrastructure.

### Gaps

- The Represent AI decision describes the internal Ghost pipeline but has no published/open gateway packaging plan. Until that is decided, an open external release must not imply that users need a private Ghost endpoint or silently introduce direct-provider key handling.
- The Orkest standalone-board and external identity details are not yet implemented. The Multica audit’s adapter contracts are a useful boundary, not proof of production interoperability or legal readiness; the setup guide requires license and hosting relationships to be rechecked for any distribution.
- No current shared schema connects Represent’s Visu/Grafe/Alegor snapshots to Orkest’s project, issue, run or session records. The Represent context explicitly says cross-tool snapshot interoperability is not claimed.
- No user research or market validation is cited here. The ladder is an architecture and product strategy recommendation grounded in the operator’s stated preference for open-source, simpler expert tools and the current company design; it is not evidence of external demand or commercial viability.
