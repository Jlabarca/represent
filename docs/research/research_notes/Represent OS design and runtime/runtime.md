# Represent OS execution architecture and runtime

Research date: 2026-10-21. This note answers a narrow architecture question: how Represent can feel like a tailored developer desktop without prematurely becoming a hosted computer platform. It separates the interface, the service that owns project state, the place code may execute, and an optional full desktop stream. Product claims and prices below are from current first-party documentation where available; provider comparisons are not benchmark results. No provider was provisioned and no paid execution was run.

## Should Represent OS be a webapp desktop, containers, or a virtual machine?

### Takeaway

Treat “Represent OS” as a webapp workspace and product metaphor first. It can present interactive Represent works, project history, and tools in a recognizable desktop layout without pretending that the UI itself is Linux. Keep execution behind a separate interface; add a real container only when a user action needs project code to run. A remote desktop VM belongs later, only if people need graphical applications or a whole remote computer.

### Cited Findings

- The current Alegor MVP is a local Node CLI/web service that captures Git history and selected documents, and calls Git with fixed argument arrays. Its server binds to loopback. Grafe is also a local Node CLI/web service that indexes captured JS/TS source through the TypeScript checker; neither source folder contains a project-code execution runner. See [Alegor core](../../../../src/alegor/core.mjs), [Alegor CLI](../../../../src/alegor/cli.mjs), [Grafe core](../../../../src/grafe/core.mjs), and [Grafe CLI](../../../../src/grafe/cli.mjs). This is evidence from the checked-out MVP source, not a claim about future product capability.
- Docker describes a container as an isolated process that shares the host kernel with other containers; a VM runs a separate operating system and kernel. Docker also documents that its daemon can be rootful and that exposing control of that daemon or mounting host files can give a container extensive host access. A container is therefore useful packaging and process isolation, but “inside Docker” alone is not a sufficient untrusted-code security design. [Docker: containers and VMs](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/); [Docker Engine security](https://docs.docker.com/engine/security/).
- Docker Rootless mode runs both daemon and containers inside a user namespace and mitigates some risks from vulnerabilities in the daemon/runtime, but its own documentation lists feature and platform limitations. It is a hardening option, not a blanket guarantee that arbitrary code is safe. [Docker Rootless mode](https://docs.docker.com/engine/security/rootless/); [Rootless limitations](https://docs.docker.com/engine/security/rootless/troubleshoot/).
- On Windows, WSL 2 runs Linux in a managed lightweight VM; its filesystem, networking, lifecycle, and Windows integration have specific behavior. Docker Desktop on Windows likewise runs Linux containers inside a Linux VM. These are convenient developer environments, but their host file sharing, lifecycle, and desktop integration are different from a production multi-tenant sandbox. [Microsoft: WSL 2 architecture](https://learn.microsoft.com/en-us/windows/wsl/about); [Docker Desktop FAQ](https://docs.docker.com/faqs/platform/).
- Cloudflare's current Sandbox documentation says its Linux container instances are microVMs with their own kernel and network, accessed through a Worker; it also offers Dynamic Workers for isolated JS/Python/Wasm execution when Linux is unnecessary. The container scheduling policy is documented as public beta. [Cloudflare Sandboxes overview](https://developers.cloudflare.com/sandbox/); [environment choice](https://developers.cloudflare.com/sandbox/concepts/choose-environment/).
- Firecracker is an open-source KVM-based microVM monitor with a narrow device model and a companion jailer; its upstream documentation describes it as infrastructure for multi-tenant workloads. Running it yourself implies operating Linux/KVM hosts, images, network policy, lifecycle, and security response. [Firecracker project](https://firecracker-microvm.github.io/).
- gVisor is a different Linux isolation approach: it implements an application kernel in userspace and can integrate through OCI `runsc`. Its docs explicitly note reduced application compatibility and higher per-system-call overhead relative to regular containers. [gVisor overview](https://gvisor.dev/docs/); [gVisor security architecture](https://gvisor.dev/docs/architecture_guide/intro/).
- The reference screenshot supplied by the user shows a chat beside a browser-based computer view with an app launcher, browser, terminal, and dock. That demonstrates the desired *interaction metaphor*. The screenshot does not establish how that computer is provisioned, isolated, billed, or persisted; the research should not infer those implementation details from pixels.

### Inferences

- Use four explicit layers: (1) **workspace UI**: desktop-like navigation, project switcher, windows/tabs, previews and task tray; (2) **Represent service/control plane**: project identity, permissions, snapshots, evidence, jobs, logs, budgets and cleanup; (3) **execution plane**: local runner or disposable remote sandbox, selected only for a task that needs execution; (4) **optional remote desktop**: graphical session stream for workflows that actually require a full GUI OS. These layers may be implemented by one process initially, but should have separate interfaces and data ownership.
- For today's local-first product, keep Grafe and Alegor deterministic work in the existing Node process and do not add a container requirement. Their current work does not execute target-project code. If a future workflow needs builds/tests, add an on-demand runner behind a narrow job API; do not place a generic shell or container socket in the webapp.
- First experiment locally with the already available environment, not by installing new infrastructure: this host reports Docker CLI 29.8.1 and a default WSL 2 Ubuntu 20.04 distribution. This was a read-only availability check only; no container was started, Docker daemon availability was not verified, and the distro was not modified. If the experiment proves useful, a disposable Docker Desktop container is a practical developer spike, with explicit resource/time limits and an isolated worktree. It is not a production multi-tenant security conclusion.
- Use a Debian slim base for the first Node/Linux job image unless a measured size/transfer concern justifies Alpine. Node's official image project says Alpine is smaller (about 25% for the cited image comparison) but uses musl rather than Debian's glibc, some glibc applications may not run, and Node's musl builds have experimental support status; Alpine variants also omit common tools such as Git and Bash. This recommendation is based on compatibility/reduced setup surprise, not on a benchmark performed for Represent. [Official Node Docker image notes](https://github.com/nodejs/docker-node).
- The user-described “leaner Dot” direction is better framed as a lean *Represent workspace*: a web UI that opens Represent artifacts and tools in context, with an optional compute session attached when needed. That keeps the appealing computer metaphor while avoiding the cost and operational obligations of keeping a desktop VM alive for users who only inspect a graph or timeline.

### Gaps

- We did not inspect Dot's backend or product implementation. The screenshot and the user's description are the only evidence about its computer environment in this task.
- There is no current Represent workload benchmark comparing local Node, a container, a browser runtime, or a remote VM. The choice should be validated against one real task and measured for setup time, task latency, resource consumption, compatibility, and cleanup.
- No identity provider, account model, hosting provider, tenancy model, region, privacy policy, or service budget has been selected. Provider pricing below cannot determine a final total cost without these choices and a workload profile.

## What is the leanest safe progression from the current MVP to code execution?

### Takeaway

Start with no code-execution service. Preserve an adapter seam for `run(job)` and implement its first useful case as a local, read-only analysis job. When a task truly requires running repository commands, prove the workflow with an ephemeral, resource-limited sandbox using a copied worktree. For hosted multi-user execution, prefer a managed microVM sandbox before operating Firecracker or a general-purpose desktop fleet yourself.

### Cited Findings

- Cloudflare says sandboxes are available on its Workers Paid plan, are reached through a Worker, and the Worker controls what data and APIs are passed to code and whether it can access the public Internet. Its containers provide a full Linux environment and microVM boundary, while Dynamic Workers can run JavaScript, Python, or WebAssembly without a Linux container. [Cloudflare Sandbox overview](https://developers.cloudflare.com/sandbox/).
- Cloudflare container pricing is metered by active runtime, with separate CPU, provisioned memory, disk, egress, Worker, and Durable Object dimensions. Its pricing page lists a $5/month Workers Paid plan with included amounts (375 vCPU-minutes, 25 GiB-hours memory, 200 GB-hours disk) and rates for additional use. The published CPU pricing is active-usage based, while memory and disk track provisioned capacity. Totals depend on instance type, active time, usage, egress, Worker/DO activity and current plan rules; a sandbox is not simply “free when no one clicks it” unless its lifecycle stops it. [Cloudflare Containers pricing](https://developers.cloudflare.com/containers/pricing/); [billing dimensions](https://developers.cloudflare.com/billing/understand/how-charges-accrue/).
- Cloudflare lifecycle documentation distinguishes the sandbox identity/ Durable Object from the running instance. Stopping an instance loses its files/processes unless the app saves a snapshot or external bucket; snapshots are currently described as public beta and expire 30 days after creation or restore. This means Represent must own durable job records and outputs outside the runtime. [Cloudflare Sandbox lifetime](https://developers.cloudflare.com/sandbox/concepts/lifetime/); [file persistence choices](https://developers.cloudflare.com/sandbox/files/).
- E2B's official pricing page says running sandboxes are billed per second. At research time it listed a free Hobby tier with a one-time $100 usage credit, up to one-hour sessions and 20 concurrent sandboxes, and a Pro plan at $150/month plus usage; its published compute rates were $0.000014 per vCPU-second and $0.0000045 per GiB-second of memory, with storage terms by plan. Pricing can change and the page's estimator requires a workload to produce a total. [E2B pricing](https://e2b.dev/pricing).
- E2B's public product pages describe a Firecracker-based microVM runtime and per-sandbox egress controls; these are vendor claims, not an independent security audit in this research. [E2B security overview](https://e2b.dev/enterprise); [E2B product overview](https://e2b.dev/).
- Daytona documents both container and Linux/Windows VM sandboxes, explicit stop/pause/archive states, persistent filesystem options, snapshots, and volume-backed data outside a sandbox. Its public docs also distinguish disk quota from billing and describe organization compute pools and tiered limits. These mechanics are relevant when comparing durable workspaces, but do not mean Represent needs those capabilities yet. [Daytona sandbox types](https://www.daytona.io/docs/en/sandboxes/); [Daytona persistence](https://www.daytona.io/docs/en/persistence/); [Daytona limits](https://www.daytona.io/docs/limits).
- WebContainers provide an alternative for browser-local JS/Node prototypes; StackBlitz documents browser sandbox execution and instant Node development environments, while its current troubleshooting guide notes that native addons are disabled by default. This makes WebContainers interesting for a narrowly web-focused, no-server preview or tutorial, not a general Linux build/test environment. The cited origin article is older and its performance/safety comparisons are the vendor's own statements, not independent benchmarks. [StackBlitz WebContainers overview](https://blog.stackblitz.com/posts/introducing-webcontainers/); [current troubleshooting](https://developer.stackblitz.com/platform/webcontainers/troubleshooting-webcontainers).
- The official Node Docker image project distinguishes Debian/glibc and Alpine/musl variants and explains compatibility implications; image size alone does not include all packages a useful build/test job needs. [nodejs/docker-node](https://github.com/nodejs/docker-node).

### Inferences

**Decision table**

| Option | Good fit | Main trade-off | Recommendation for Represent |
|---|---|---|---|
| Webapp “OS” shell, no execution | Open Grafe graphs, Alegor timelines, Visu works, evidence drawers and saved project views | Cannot run arbitrary build/test commands by itself | **Build this as the product surface now.** |
| Local Node process/agent | Deterministic scanning, Git and docs access for one developer; simplest development and offline path | Runs with the local user's permissions; must not be sold as isolation for hostile code | Keep as the current local core and future local connector. |
| Browser WebContainer | Fast sandboxed JS/Node demo, exercise or small web preview | Limited compatibility versus full Linux; browser support and native-addon constraints; not a place for unrestricted project data or general system tools | Optional experiment only if a browser-only JS preview has proven user value. |
| Rootless local container | Reproducible one-off build/test job across developer machines | Host still shares Linux kernel; rootless mode has constraints; Docker installation and image maintenance add setup work | Use for a local disposable spike after identifying a real run command. |
| Managed hosted container/microVM (Cloudflare Sandbox, E2B, Daytona) | On-demand build/test/agent work with a separate execution boundary and provider lifecycle primitives | Usage charges, vendor coupling, data transfer, provider limits and persistence design | Best later hosted pilot; compare Cloudflare against E2B on the same controlled task before choosing. Daytona is useful as a persistent-workspace comparison. |
| Self-operated gVisor or Firecracker fleet | Platform team that needs workload isolation control and can run Linux infrastructure | Kernel/runtime operations, sandbox hardening, network/tenant controls, incident response, image pipeline and 24/7 reliability | Defer until usage and product requirements justify owning infrastructure. |
| Full remote desktop VM | GUI-only apps, visual browser control, persistent complete desktop or OS-specific workflow | Highest lifecycle, streaming, storage, session and isolation burden; many current Represent tasks do not need it | Treat as a distinct later capability, only after a task demands it. |

**Phased architecture recommendation**

1. **Now — Represent workspace, no sandbox.** Build the desktop-like navigation around project identity and interactive artifacts. Apps are web modules/views. Save snapshot metadata and the artifacts themselves through the existing explicit/manual snapshot actions. Alegor remains the re-entry/history lens; Grafe remains the structural code lens; Visu remains paused until resumed by the user. Keep Ghost as the only future AI gateway.
2. **Local runner contract — no arbitrary shell UI.** Define a small job record (`jobId`, project/snapshot ID, requested task, declared permissions, status, start/end, exit result, bounded logs, resource budget, output artifact manifest). Route allowlisted job types through a local process API. For the first spike, run only a deterministic `git status`/test command against a disposable copy; provide argv as an array, fixed working directory, environment allowlist, time/resource cap, output cap, cancellation, and cleanup. No credentials, shell-string interpolation, Docker socket mount, or implicit writes to the user's working tree.
3. **Optional container adapter.** Once a real job benefits from a Linux image, run it on demand with a pinned Debian slim image and resource/time/network bounds. Mount only an explicit snapshot/worktree, read-only by default; if a task may edit, create a disposable branch/worktree and export a patch/artifact for a person to review. Save job status, logs and outputs outside the container; stop/destroy even on cancellation or failure. Test cold-start, repeated-job cache, no-network behavior, filesystem escape tests, output limits and cleanup before making this public.
4. **Hosted pilot.** Compare Cloudflare Sandbox and E2B using the same real job and sample repo; compare Daytona if persistent filesystem/VM pause matters. Measure creation and resume latency, monthly idle/storage cost, active cost, data upload/download, cold cache setup, network allowlist behavior, cancellation, per-user isolation, and export/delete semantics. Use synthetic or public repositories first. Keep API keys in the control plane and pass only short-lived, job-scoped credentials if absolutely necessary. Don't commit to a provider or incur cost until there is a verified use case and a budget decision.
5. **Desktop only on evidence.** Add a streamed Linux desktop only if users need applications that cannot be represented as a browser view, terminal or preview. Keep the desktop ephemeral by default and preserve project data and screenshots separately; do not make “always-on VM” the default way to open a graph.

### Gaps

- Published provider pricing is a moving snapshot; no complete comparative bill was calculated because target usage, regions, persistence and requests are not known. Recheck official pricing immediately before any provider trial.
- E2B's product and security statements were not independently validated, and no SDK or runtime was installed. Cloudflare and Daytona were researched from official docs only; neither was exercised.
- No representative code-execution workload has been chosen. A `npm test` run on one repository would provide a useful spike, but would not establish safe handling of arbitrary code or all project languages.
- The account's actual Cloudflare/E2B/Daytona plan eligibility, regional availability, account budgets and data-processing terms remain unknown.

## How should interactive Represent artifacts be previewed and kept separate from execution?

### Takeaway

The sandbox that runs a build or agent does **not** protect the main web app from an HTML/JavaScript artifact loaded into the app's own origin. Treat preview as a browser security boundary of its own: start with data-rendered artifacts in trusted Represent components; serve arbitrary HTML/JS from a separate origin inside a sandboxed iframe with no unnecessary capabilities; communicate through a tiny typed message bridge.

### Cited Findings

- The browser same-origin policy restricts one origin's scripts from reading another origin's data, and the origin is the scheme, host, and port. It is not a container boundary, and embedding alone has allowed interactions that need separate controls. [MDN: same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy); [MDN: origin](https://developer.mozilla.org/en-US/docs/Glossary/Origin).
- The iframe `sandbox` attribute imposes restrictions that can be re-enabled one capability at a time. MDN warns not to combine `allow-scripts` and `allow-same-origin` for same-origin embedded content because it could remove the sandbox attribute and reload. MDN also recommends serving potentially malicious user-generated content from another domain when it may be visited directly. [MDN: iframe sandboxing and embedding](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/General_embedding_technologies); [MDN CSP sandbox directive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox).
- Cross-origin frames should communicate through `postMessage`; MDN advises validating the sender's origin and source, validating message syntax, and using an exact target origin instead of `*` when possible. [MDN: `window.postMessage`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage.).
- Cloudflare's execution docs describe what a sandbox can access as a function of data, APIs and network granted to it. That controls code execution. It does not automatically change the browser origin in which an artifact preview is served. [Cloudflare Sandbox overview](https://developers.cloudflare.com/sandbox/); [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy).

### Inferences

- **Represent artifact MVP:** prefer a structured artifact schema (nodes, edges, timeline events, media references, approved interactions) and render it through trusted React/Vue/Canvas components. This makes “interactive” useful without executing generated HTML inside the parent app.
- For a user-supplied or generated arbitrary HTML/JS preview, use a dedicated preview host/site with no Represent app cookies or authenticated API on that origin. Embed it in an iframe with the smallest required `sandbox` flags; keep `allow-top-navigation`, popups, downloads, forms, camera/microphone, clipboard and broad network access off unless a named feature needs one. CSP should start restrictive and permit only the resource classes the artifact needs. Consider whether the artifact can load external scripts or make network requests; default these off or allowlist them.
- If a bridge is required, expose only explicit messages such as `ready`, `resize`, `select-node`, or `open-evidence`. Check the iframe window reference, expected origin where available, payload schema/size and an unguessable per-preview nonce; never expose app tokens, arbitrary API calls, shell commands or path access through the bridge. For sandboxed frames with an opaque origin, rely on `event.source` and the per-frame nonce and never send secrets to the frame; test the actual browser behavior before shipping.
- Keep **execution results** and **presentation artifacts** separate: a job may produce a JSON result plus bounded logs and files; a separate preview service turns the allowed artifact format into a view. Persist each with job ID, source snapshot ID, content hashes and provenance. The UI can open the result like a desktop app without giving that artifact access to Alegor history, Grafe source or the user account.
- Add a boundary-focused spike before accepting arbitrary generated web bundles: verify the frame cannot read app storage/cookies, invoke app APIs, escape to the top window, or retain privileges after a reload; verify the bridge rejects forged origin/source/payloads; verify direct navigation to the preview origin exposes no account session. These are concrete tests for the chosen preview boundary, not a claim that CSP or iframe sandboxing alone makes arbitrary code universally safe.

### Gaps

- Current Grafe and Alegor do not render untrusted executable HTML bundles. This recommendation is forward-looking for “interactive Represent works,” and the exact preview artifact schema is not designed yet.
- A dedicated registrable domain, preview host, CSP policy, authentication model and browser-support target have not been selected. A deployment should be reviewed against the actual artifact feature set and current browser behavior.
- This research did not inspect Dot's preview internals or run a browser security test against a Represent artifact; no test or provider deployment was performed.
